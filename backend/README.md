# UniMatch — backend (FastAPI), синхронизирован с app.js

Этот бэкенд соответствует текущей версии фронтенда (`index.html` + `app.js`),
который до недавнего времени работал полностью локально: онбординг, свайпы и
весь скоринг (Match Score, Admission Reality, University DNA, "Why this
university") считались прямо в JS и сохранялись в `localStorage`. Теперь
`app.js` реально обращается к этому бэкенду через `fetch()` — см. README
фронтенда.

## Исправлено при интеграции с реальным app.js

- **`schemas.py`/`main.py`: у `UserOut` не было числового `id`.** Отдавался
  только `guestId` (строка-токен) — а `app.js` использует именно числовой
  `user_id` в путях вида `/users/{id}/swipes`, `/users/{id}/matches` и т.д.
  Без этого поля фронт физически не мог сделать ни одного запроса после
  создания пользователя. Добавил `id: int` в `UserOut` и `_user_out()`.
- **Добавлен `DELETE /users/{user_id}/swipes/{university_id}`.** На странице
  вуза есть кнопка "Save"/"In Matches", которая должна и добавлять, и убирать
  вуз из Matches. Раньше на бэке была только запись свайпа (`POST`), без
  возможности отменить.
- (Из прошлого ревью) `schemas.py`: клампинг `TestEntry.score` был no-op —
  перенёс на уровень `Tests`, где известно, какому тесту принадлежит `score`.
- (Из прошлого ревью) `models.py`: `default=lambda: dict(DEFAULT_TESTS)` —
  мелкая копия; заменил на `copy.deepcopy`.

## Что изменилось по сравнению с самой первой версией бэкенда

- **Профиль пользователя** — три независимых теста (`tests.SAT/ACT/IELTS`,
  каждый со своим `taken`/`score`), а не один `test_type`/`test_score`. Плюс
  `degreeLevel` (`bachelor`/`master`/`phd`) и `lang` (`ru`/`en`).
- **Admission Reality** — считается через сравнение GPA/SAT с реальным средним
  диапазоном поступивших (25-й/75-й перцентиль: `gpa25`, `gpa75`, `sat25`,
  `sat75` у каждого вуза), а не через "сила профиля vs общий acceptance rate".
- **API отдаёт camelCase**, как и объекты во фронтенде (`matchScore`,
  `admissionReality`, `degreeLevel`, `needsAid` и т.д.).
- **Форма `UserOut`/`UserCreate`** повторяет то, что раньше лежало в
  `localStorage.unimatch_guest_v1`: `{id, guestId, isRegistered, email, lang,
  profile: {...}}`.
- **Добавлен CORS** — `app.js` открывается с `127.0.0.1:5500` (Live Server и
  т.п.), без `CORSMiddleware` браузер молча блокирует все запросы к API.
- **Данные вузов** (`seed_data.py`) распарсены прямо из константы
  `UNIVERSITIES` во фронтенде, а не перепечатаны вручную.

## Решения по трём открытым вопросам (см. обсуждение)

1. **Majors** — вариант A: скоуп ограничен CS (`cs` — единственное поле силы
   программы). Фронт даёт выбрать любую специальность из `MAJOR_CATEGORIES`,
   но это осознанное ограничение MVP.
2. **Фото вузов** — не хранятся в БД. Фото MIT остаётся зашитым в
   `UNIVERSITIES` на фронте; `app.js` подмешивает его к ответу бэкенда по
   `id` (см. функцию `fromApiUni()`).
3. **Локализация "Why this university"** — вариант D в API готов
   (`/universities/{id}/why` отдаёт `{code, params}` + `breakdown`), но
   **на практике `app.js` пока продолжает считать Why/breakdown локально**
   (`buildWhyReasons`, `matchBreakdown`) — это чистые функции без побочных
   эффектов и без запроса к серверу они не нуждаются. Эндпоинт остаётся
   готовым к использованию, если позже понадобится, например, сохранять
   персонализированные объяснения.

## Что осталось не реализовано (сознательно, фаза 2)

- Настоящий recommendation engine (cosine similarity / KNN / clustering).
- Токены-сессии/JWT: вход возвращает `UserOut`, но защищённых ручек нет —
  API остаётся доверительным (демо). При выносе в прод добавить токены.
- `degreeLevel` не участвует в фильтрации/скоринге — как и на фронте.
- Отдельного счётчика "passed" (дизлайков) на бэке нет — `app.js` считает
  его локально за текущую сессию (не переживает перезагрузку страницы).
  При желании можно добавить `GET /users/{id}/swipes?liked=false`.

## Синхронизация с текущим контрактом фронтенда (profile)

Приложенный фронтенд (`app.js`) давно ушёл вперёд старой схемы, и `POST /users`
падал 422 ещё до всякой авторизации. Синхронизировано:

- **`size`/`setting`/`climate` — теперь массивы** (мульти-выбор на онбординге),
  а не одиночные строки. В БД (VARCHAR-колонки) хранятся как JSON; легаси-строки
  из старых баз читаются как массив из одного элемента (`_list_from_db`).
- **Тестов теперь семь**: SAT/ACT/IELTS + TOEFL/DET (английский) + IB/EGE
  (академические) — как `TEST_RANGES` во фронтенде. Клампинг баллов расширен
  на все семь.
- **`homeCountry`/`nativeLang`** — новые поля профиля (шаг "About you"),
  хранятся в новых колонках `home_country`/`native_lang` (докидываются миграцией).
- `scoring.py` научился работать с массивами предпочтений (`_pref_match`) и
  считать IB/EGE в SAT-эквиваленте для Admission Reality. Фронт всё равно
  пересчитывает Match Score локально для отображения — серверный скоринг влияет
  только на порядок колоды в `GET /universities`.

## Настоящая регистрация и вход (/auth/register, /auth/login)

`POST /auth/register` и `POST /auth/login` — ровно тот контракт, который ждёт
фронтенд (`submitAuthForm` → `apiAuthRegister` / `apiAuthLogin`):

- **`POST /auth/register`** — `{email, password, lang, guestId}` → `UserOut`
  (тот же объект, что отдают `/users` и `/users/{id}`).
  - Пароль — минимум 6 символов (как `minlength` на фронте), хранится только
    как PBKDF2-HMAC-SHA256-хеш с солью (`auth.py`, только stdlib, без внешних
    зависимостей). В ответах пароля и хеша никогда нет.
  - `guestId` опционален: если передан и есть в БД, email+пароль привязываются
    к текущему гостю — профиль, свайпы и Matches сохраняются («усыновление»).
    Без `guestId` создаётся новый пользователь с дефолтным профилем.
  - Email нормализуется (trim + lower), дубликаты → 400 "Этот email уже
    привязан к другому аккаунту". Аккаунт после "мягкой" регистрации (email
    без пароля) может до-регистрировать пароль этим же эндпоинтом — список
    не потеряется.
- **`POST /auth/login`** — `{email, password}` → `UserOut` + `sessionToken`.
  Неверный пароль и несуществующий email отвечают одинаково (401 "Неверный
  email или пароль"), чтобы не раскрывать, есть ли аккаунт.
- **`POST /auth/logout`** — удаляет текущую сессию по Bearer-токену (фронт
  зовёт из кнопки «Выйти» в сайдбаре).
- `POST /users/{id}/register` ("мягкая" привязка email без пароля) остаётся
  для совместимости; гостевой баннер на фронте теперь ведёт на полный экран
  регистрации.

### Серверные сессии и контроль доступа

`/auth/register` и `/auth/login` выдают непрозрачный токен сессии
(`auth_sessions` в БД, `secrets.token_urlsafe`), фронт хранит его отдельно от
гостевой сессии (`unimatch_auth_v1` в localStorage) и шлёт во все запросы как
`Authorization: Bearer <token>`.

Персональные данные **зарегистрированного** пользователя (профиль, свайпы,
Matches, DNA, смена профиля через `POST /users`) бэкенд отдаёт только с
валидным токеном — знание числового id или guestId чужого аккаунта больше не
даёт доступ. **Гость** остаётся на демо-модели: его «пароль» — секретный
guestId, который клиент шлёт в `POST /users`.

Защита от захвата аккаунта в `/auth/register`:

- email уже занят аккаунтом с паролем → 400 (даже со своим guestId);
- гостевая сессия уже привязана к аккаунту с паролем → 400 «Эта сессия уже
  привязана к аккаунту — войди» (иначе регистрация перезаписала бы аккаунт);
- до-регистрация пароля на «мягкий» email-аккаунт — только с guestId-пруфом
  владения этим же аккаунтом, иначе 400.

### Миграция существующей БД

`create_all` не добавляет колонки в уже существующие таблицы, поэтому при
старте `main.py` проверяет схему SQLite и докидывает `users.password_hash`
через `ALTER TABLE`, если база создана старой версией кода (проверено на
реальной БД со старой схемой: пользователи, свайпы и вузы остаются на
месте). Для PostgreSQL это дело Alembic.

## Интеграционный тест

`test_auth.py` — 46 проверок против поднятого сервера: сценарий гостя →
свайпы → регистрация (прогресс сохраняется, токен выдан) → контроль доступа
(персональные ручки без/с чужим токеном → 401) → логин (верный/неверный
пароль, несуществующий email) → защита от захвата аккаунта (дубли email,
перезапись сессии, до-регистрация без пруфа) → апгрейд мягкой регистрации →
выход (токен умирает, соседняя сессия живёт) → проверка, что в БД лежит хеш,
а не пароль. Запуск:

```bash
uvicorn main:app &
PORT=8000 python3 test_auth.py   # ожидает 46 ok, 0 fail
```

Поверх этого прогнан полный UI E2E в реальном Chromium (Playwright, фронт
отдаётся локально поверх HTTP): лендинг → онбординг (5 шагов) → лайки →
регистрация через форму → reload (сессия восстановлена) → «Выйти» → вход →
изоляция аккаунтов (второй пользователь не читает данные первого, перехват
email отклонён, пароль не скомпрометирован) — 20/20.

## Структура

```
backend/
├── main.py          # FastAPI приложение и роуты (+ CORS, + /auth/*, + миграция SQLite)
├── auth.py          # PBKDF2-HMAC-SHA256 хеширование паролей (только stdlib)
├── database.py       # подключение к БД (SQLite для локальной разработки)
├── models.py         # SQLAlchemy модели: User (+password_hash), University, Swipe
├── schemas.py        # Pydantic-схемы, camelCase-алиасы под фронт (+ AuthRegister/AuthLogin)
├── scoring.py         # Match Score / Admission Reality / Why — портированы из JS
├── seed_data.py       # 50 вузов, распарсенные из фронтенда
├── test_scoring.py    # 25 unit-проверок scoring.py, без внешних зависимостей
├── test_auth.py      # 46 интеграционных проверок авторизации и сессий
└── requirements.txt
```

## Как запустить

```bash
pip install -r requirements.txt
python seed_data.py          # создаёт unimatch.db и заливает 50 университетов
uvicorn main:app --reload    # http://127.0.0.1:8000/docs
```

Проверить только логику скоринга (без установки FastAPI/SQLAlchemy):
```bash
python3 test_scoring.py
```

Фронт (`app.js`) стучится на `http://127.0.0.1:8000` (константа `API_BASE`
в начале файла) — если запускаешь бэкенд на другом порту/хосте, поменяй эту
константу.

## API

- `POST /users` — создать/обновить гостевой профиль
- `POST /auth/register` — настоящая регистрация: email + пароль (PBKDF2-хеш),
  опционально «усыновляет» гостя по `guestId`
- `POST /auth/login` — вход по email + паролю
- `POST /users/{id}/register` — оставить email без пароля ("мягкая" регистрация,
  для совместимости)
- `GET /users/{id}` — получить профиль
- `GET /universities?user_id=` — deck, отфильтрованный по `profile.continents/countries`
  пользователя, отсортированный по Match Score
- `GET /universities/{id}/why?user_id=` — причины + breakdown по категориям
  (эндпоинт готов, но `app.js` пока считает это локально — см. выше)
- `POST /users/{id}/swipes` — записать like/dislike
- `DELETE /users/{id}/swipes/{university_id}` — отменить свайп (кнопка "Save"
  на детальной странице вуза)
- `GET /users/{id}/matches` — лайкнутые вузы с Match Score / Admission Reality
- `GET /users/{id}/dna` — University DNA (эндпоинт готов, но `app.js` пока
  считает это локально из уже загруженного `state.liked` — см. выше)

## Как перейти на боевую БД

Замените строку подключения в `database.py` на PostgreSQL и добавьте Alembic —
остальной код не меняется, вся работа идёт через SQLAlchemy ORM.
